# 2026-10-29 음성 입력 불안정 조사

## 현재 결론

서버 요청 분류 오류와 녹음 시작 대기를 각각 재현하고 수정했다. Windows SV(호스트명 SB)에 1.1.71을 설치했다. 그러나 기존 FP16 음성 인식의 성능 저하 원인은 아직 확정하지 못했으며, 속도 문제가 해결됐다고 판단하지 않는다.

이 문서는 앱 코드의 오류와 GPU 성능 문제를 구분하기 위한 중간 조사 기록이다. Mac·Fold7은 SV 서버를 사용하므로 서버의 지연이나 실패가 함께 나타날 수 있다.

## 확인된 오류와 수정

### 짧게 나뉘어 도착하는 HTTP 요청

서버는 처음 네 바이트를 확인해 HTTP POST와 WebSocket 요청을 구분한다. 기존 코드는 데이터를 소비하지 않는 `peek` 결과를 새 데이터처럼 이어 붙였다. `POST`가 여러 패킷으로 나뉘어 도착하면 `PPPP` 같은 잘못된 접두사를 만들 수 있었다.

실제 설치본에서 인증 없는 완전한 POST는 HTTP 403이었지만, 첫 1~3바이트를 먼저 보낸 POST는 연결만 종료됐다. 수정 후 네 경우 모두 정상적으로 HTTP 403을 반환했다. 인증을 완화한 것이 아니라 요청 분류를 고친 것이다.

수정은 같은 네 바이트 버퍼를 다시 확인하고, 불완전한 접두사의 대기를 5초로 제한한다. 연결 종료를 처리하고 짧은 대기 간격으로 busy loop를 방지한다.

### 다른 전사 작업 때문에 녹음 시작이 지연되는 문제

일반 녹음과 바로입력의 연결 단계가 공유 음성 인식 서비스의 잠금을 얻고 모델 준비를 기다렸다. 다른 기기의 느린 전사가 진행 중이면 마이크 준비도 대기할 수 있었다.

녹음 데이터 수집과 모델 추론은 별개이므로 연결 단계의 불필요한 모델 준비 대기를 제거했다. 기존 앱 시작 시 pre-warm, 실제 전사, 녹음 형식 검증, 취소와 입력 대상 보호는 유지했다. 공유 잠금을 잡아 둔 상태에서도 두 연결 경로가 준비되고 음성 버퍼가 유지되는 테스트를 추가했다.

## 검증된 범위

- Rust 전체: 750 passed, 0 failed, 기존 3 ignored. 별도 integration 그룹 5 + 1 + 3 passed.
- Tauri production 빌드: 프런트엔드 타입 검사·Vite 빌드를 포함해 통과.
- 실제 SV 설치본: 분할 POST 네 경우의 인증 거부 응답 정상.
- 실제 Fold7: 기존 앱의 서버 연결·인증 확인, 키보드 준비/취소 및 안전하지 않은 입력 대상 거부 QA 통과. 임시 QA 앱은 제거했다.
- 실제 Mac → SV HTTPS: 합성 음성의 전사와 AI 다듬기 요청 성공. 다만 여전히 느렸으며 실제 사람의 마이크 → 커서 입력 검증은 아니다.

## 아직 해결되지 않은 FP16 속도 저하

3.255초 합성 음성의 현재 FP16 전사는 약 9~26초가 걸리는 사례가 있었고, 60초 전사 제한에 걸리는 사례도 있었다. 모델 초기화 자체가 120초 제한에 걸리는 현상도 확인했다. 이는 정상 속도로 인정하는 기준이 아니라 현재 장애 상태의 측정치다.

Mac의 한 요청은 서버 로그상 STT 약 13.6초, AI 다듬기 약 4.0초였다. 따라서 모든 지연을 AI 추론 강도 때문이라고 설명할 수 없다.

다음은 확인했지만 원인으로 확정하지 않았다.

- 모델 SHA256은 최초 고정된 파일과 동일하다. 모델·라이브러리·프롬프트를 바꾸지 않았다.
- GPU 예산 조회에서 해당 추론 프로세스의 local budget 약 7,250 MiB, usage 약 4,058 MiB였다. 단순 VRAM 부족이라고 단정할 근거는 없다.
- 프로세스 CPU/메모리 우선순위를 각각 정상화한 제한적 시험으로는 원래 속도가 복구되지 않았다. 시스템 전역 정책은 바꾸지 않았다.
- GPU는 추론 시 고성능 상태로 올라갔다. 계속 저전력 상태에 고정됐다는 가설은 확인되지 않았다.
- allocator 변경 시험은 모델 초기화 제한에 걸려 채택하지 않았다.
- 같은 FP16 모델의 main/worker thread 비교는 모델 생성 단계에서 제한에 걸렸다. thread 차이를 원인으로 확정할 수 없다.

사용자가 그래픽 재초기화를 승인하고 `Win+Ctrl+Shift+B`를 직접 눌렀다고 확인했다. 자동화 도구의 Windows 키 제한을 우회하지 않았다. 이후 같은 설치본·같은 FP16 설정으로 앱만 재시작했지만 초기화는 다시 120초 제한에 걸렸다. 제한된 별도 로딩 추적에서도 `faster_whisper/transcribe.py:689`의 `ctranslate2.models.Whisper(...)` 호출이 20초·40초 시점에 반환하지 않았다. DLL 준비와 CUDA 지원 확인은 약 86ms 이내에 통과했다. 이 증거는 대기 위치를 좁히지만 드라이버나 라이브러리 자체의 결함을 확정하지는 않는다.

추적 후 원래 앱을 복구했을 때는 모델 준비가 약 58.5초 후 완료됐으나, 이어진 실제 전사 요청은 약 64.0초 후 실패했다. 다음 요청도 약 1.4초 후 실패했다. HTTP 200 응답 안에 실패 JSON이 들어 있으므로 상태 코드만으로 성공이라고 판단하지 않았다. 재초기화로 복구됐다는 결론은 내릴 수 없다.

추가로 앱을 일반 사용자·Normal CPU 우선순위·메모리 우선순위 5인 독립 실행 문맥에서 시작해 상속된 백그라운드 자원 정책을 분리 시험했다. 앱과 두 Python 실행 단계 모두 해당 우선순위를 확인했지만 첫 요청은 100초 클라이언트 제한에 걸렸고 다음 요청도 실패했다. 이것도 해결책으로 채택할 근거가 없다. 실행용 일회성 작업은 삭제했으며 자동 실행 설정은 변경하지 않았다. 결과는 `qa/incident-20261029/service-after-normal-context.json`에 있다. 이 동작들은 새 드라이버 설치나 PC 재부팅이 아니다.

## 저메모리 계산 방식은 보류

16:24 이후 사용자가 SB 전체 부하 복구 중임을 알려 읽기 전용으로 확인했다. 새 전사 없이 CPU 평균 60.1%/최고 69.4%, 별도 측정의 kernel 처리 약 37.2%, RTX3070 메모리 약 79%였다. RAM available 약 16.5 GiB, 디스크 queue 0으로 당시 RAM·디스크 포화는 확인되지 않았다. 현재 시스템 부하가 지연을 악화시켰을 가능성을 배제할 수 없다. 이전 FP16/INT8 시험 때 전체 자원을 동시에 측정하지 않았으므로 그 차이를 엔진 자체 결함으로 확정하지 않는다. SB 복구 후 원래 FP16을 먼저 재검증하는 방향으로 두고 정밀도 변경은 보류한다. 상세: 프로젝트 상위 `qa/incident-20261029/HOST-LOAD-REVIEW.md`.

별도 시험의 `int8_float16`은 빨랐고 제한된 한국어 표본의 핵심 정보를 보존했다. 다만 일부 FP16/INT8 측정에서 실행 thread 등 비교 조건이 달랐으며, 이것만으로 속도 차이 전체를 정밀도에 귀속하거나 품질 동등성을 보장할 수 없다.

재초기화 후에는 같은 `WhisperRecognizer` 생성 경로에서 진단용 자식 프로세스의 계산 방식만 `int8_float16`으로 바꾸고, FP16 추적과 같은 CPU/메모리 우선순위에서 추가 비교했다. 모델 준비 6,625ms, 같은 합성 음성의 worker 전사 797ms / main 전사 453ms였고 핵심 정보가 보존됐다. 서비스 코드나 설정의 계산 방식은 바꾸지 않았다. 따라서 앞선 thread 차이만으로 모든 지연을 설명할 수 없고, 현재 FP16 모델 준비/실행 경로에 문제가 집중된다는 근거가 추가됐다. GPU 메모리 부족 또는 드라이버 내부 결함이라는 세부 원인은 여전히 확정하지 않았다.

사용자는 기존 FP16이 느려진 이유부터 확인하라고 요청했다. 실제 서비스 정밀도는 여전히 `float16`이며, 양자화·모델 교체·AI 모델 변경은 적용하지 않았다.

서비스 복구를 위해 SV만 저메모리 방식으로 임시 전환할지 사용자에게 명시적으로 질문한 상태다. 응답 전에는 전환하지 않는다. 질문 제시는 승인이나 설치 완료를 뜻하지 않는다.
