# 모바일 버튼 사용성 개선과 최근 변경 검토

## 최근 변경은 실제로 무엇을 개선하나요?

검토 기준은 최상단 표시 수정 `8609461`과 입력 복구·대상 보호 `9f480dd`다. 후자는 검토 시작 당시 로컬 main에만 있었고, 설치된 Android는 여전히 .9였다. 새 소스의 기능을 기존 설치 앱에서 이미 사용 중이라고 간주하지 않았다.

| 변경 | 확인 가능한 효과 | 성능·한계 |
| --- | --- | --- |
| 데스크톱 최상단 표시 | Home 사용자 확인과 실제 Windows 창 순서 회귀 검사로 가려짐 복구 확인 | STT/LLM 속도 개선이 아님. 작업 중 초당 한 번 창 순서 복구 |
| 실패 결과 복구 | 자동 입력 실패 후 전문 또는 확보한 부분을 수동 복사할 경로 제공. 명시 취소·오래된 세션 응답은 보존하지 않음 | 데스크톱 최근 20개, Android 마지막 1개만 메모리 보관. 앱 프로세스 종료 시 소멸 |
| 데스크톱 입력 대상 보호 | 같은 앱의 다른 창·다른 입력 요소로 바뀌어도 자동 입력을 막는 검사 추가 | 확인 불가한 편집기도 차단하므로 호환성 실기 검증 필요. 모델·프롬프트·전사 경로는 그대로 |
| Windows UIA 검사 | 조회 실패 시 잘못된 자동 입력을 허용하지 않음 | 150ms는 호출자의 대기 제한이다. COM 작업 자체를 취소하지 않으며 단일 worker에 영구 정지가 생기면 후속 UIA 검사도 실패할 수 있음. 실제 정지는 재현하지 않았지만 코드상 배포 전 검토 사항 |
| 스트리밍 대상 확인 | 각 chunk와 최종 suffix 전에 대상 변경 검사 | chunk마다 조회 비용이 추가된다. 전체 받아쓰기 속도가 빨라졌다는 근거는 없으며 느려질 가능성이 있음 |

이번 검토에서 frontend **423개**, Windows Rust **638개/실패 0/기존 ignored 3개**를 직접 다시 실행해 통과했다. 이는 논리 회귀 검증이지 실제 음성 왕복 시간·평균·p95의 측정이 아니다. Mac의 새 대상 보호 코드는 이번에 빌드·설치하지 않았다. PC·Mac 운영 앱과 서버를 교체하지 않았다.

Android `AccessibilityInputConnection.commitText`는 앱에서 반환값으로 실제 삽입 여부를 확정할 수 없는 경로다. 오류를 반환하지 않고 대상 앱이 입력을 무시하는 경우까지 복구 기능이 완전히 감지한다고 주장하지 않는다. 복구 UI는 실패 결과를 다시 모델에 요청하거나 자동 재입력하지 않으므로 오입력 방지와 수동 구제에 의미가 있지만, 처리 속도를 높이는 기능은 아니다.

## 버튼 겹침의 원인과 수정

기존 배치는 키보드 상단에서 64dp만 올렸고, 키보드가 없으면 입력칸 아래에 놓았다. 즉 보내기 버튼이 있는 행과 겹칠 수 있었다. 즉시 드래그는 long-press만 취소하고 위치는 바꾸지 않는 구현이었다.

기존 위치 계산을 실제 호출부에서 공유 함수로 분리한 뒤, “입력칸 위 48dp 이상 간격” 검사가 실패하는 것을 확인했다. 이후 다음과 같이 수정했다.

- 기본 위치: 마이크 터치 영역의 아래쪽이 입력칸 상단보다 **48dp 이상 위**에 오도록 배치. 키보드가 보이면 키보드 상단과도 **112dp 이상** 간격을 둔다. 화면 위 공간이 부족하면 안전 영역 안으로 제한한다.
- 크기: 원 **48→56dp**, 터치 영역 **56→64dp**. 대기 불투명도 **90→74%**. 녹음 중 중앙창은 기존 디자인을 유지한다.
- 짧게 터치: 녹음 시작. 버튼을 누르고 시스템 touch slop 이상 바로 이동: **위치 이동**, 녹음/모드 변경 없음.
- 가만히 길게 누르기: 시스템 long-press 시간 후 **진동과 모드 메뉴**. 이후 드래그는 모드 선택이며 위치 이동과 혼동하지 않는다.
- 드래그 취소·다중 터치: 녹음이나 모드 변경 없이 중단. 이동 취소는 이전 위치로 복원.
- 이동 위치는 좌표 비율만 앱 설정에 보존. 화면 회전·접힘·키보드 변화 때 화면 밖으로 나가지 않게 제한하며 임시 제한으로 저장값을 덮어쓰지 않는다.
- 왼쪽으로 옮기면 모드 메뉴는 오른쪽으로 펼쳐진다. 화면 위·아래 가장자리에서는 메뉴를 화면 안으로 조정한다.
- 앱 설정의 **마이크 위치 초기화**로 높아진 기본 배치로 돌아간다. 수동 위치도 현재 입력칸 위 안전 영역으로 제한한다. 다른 앱의 입력칸이 더 높거나 여러 줄로 커져도 저장 좌표 때문에 다시 보내기 행을 가리지 않게 한다. 개별 보내기 버튼의 의미를 추측하거나 화면 내용을 수집하지 않는다.

터치 판정은 [Android ViewConfiguration](https://developer.android.com/reference/android/view/ViewConfiguration)의 시스템 임계값을 사용한다. 상태바·화면 잘림 영역은 [WindowInsets](https://developer.android.com/reference/android/view/WindowInsets)로 제외한다. 새로운 의존성·권한·DNS/VPN·서버 인증 변경은 없다.

## 검증과 배포 범위

### 검증 중 발견한 녹음 시작 취소 문제

실제 ChatGPT·Grok의 첫 검사에서 정상 입력칸인데도 녹음 시작이 취소됐다. 단순 재시도 성공을 해결로 간주하지 않고, 기존 `paused` 실기기 시나리오와 외부 앱 진입을 교대로 반복했다. `paused`에서 8/8 실패했고, 내용이 아닌 상태 boolean 진단으로 **동일한 입력 요소·유효한 연결·표시 상태인데 원래 Activity가 pause되고 녹음 Activity는 아직 resume되지 않은 순간**의 포커스 손실을 확인했다.

녹음창 시작부터 `beginCapture`까지 전환 단계를 명시했다. 이 짧은 단계에서만 주기적인 입력칸 재검색을 미루고, **녹음 시작 직전에 기존의 내용·커서·연결·대상 검사를 그대로 수행**한다. 전환이 2.5초 안에 끝나지 않으면 취소한다. 실제 텍스트 변경·입력 연결 종료·명시 취소의 보호는 해제하지 않았다. 수정 후 동일 pause 시나리오 5회 연속 통과, 전환 중 실제 내용 변경을 만드는 `launch-edit`도 안전 취소됐다. 임시 진단 코드는 제거했다. 최초 실제 앱 실패가 모두 이 원인이었다고 단정하지는 않지만, 재현 가능한 전환 경쟁 조건은 수정했다.

이후 **앱 설정 화면 방문 → 외부 입력칸 → 녹음** 순서에서 두 번째 문제가 재현됐다. 연결·내용·커서는 같아도 `captured.refresh()`가 실패했고, 설정 화면을 열기 전에는 반복 녹음이 통과했다. 설정과 녹음 Activity가 같은 task affinity를 공유해 `NEW_TASK` 실행이 기존 설정 task를 앞에 가져오는 구조였다. 녹음 Activity의 `taskAffinity`를 빈 값으로 분리했다. 설정 화면·인증 데이터를 지우거나 대상 검사를 완화하지 않는다. [공식 Activity taskAffinity 설명](https://developer.android.com/guide/topics/manifest/activity-element#aff) · [task와 back stack](https://developer.android.com/guide/components/activities/tasks-and-back-stack).

`bubble-gestures` 검사는 이제 설정의 위치 초기화 버튼을 실제로 누른 뒤 외부 QA 편집기로 넘어간다. 따라서 기본 배치 검사의 초기 조건뿐 아니라 설정 방문 후 녹음 실패도 함께 잡는다. 이전에 저장된 수동 위치를 기본 위치로 오인하던 QA 전제와 nullable 접근성 텍스트 처리도 보완했다.

- Android Java **114개** 검사 통과: 위치 간격, 긴 입력칸, 수동 위치의 보내기 행 회피, 경계, 저장 좌표 복원, 즉시 드래그/long-press 구분, 취소·다중 터치 상태, 왼쪽 반원 선택.
- APK/QA 빌드, 앱·QA Lint, 기존 키의 v2 서명 확인 통과.
- 갤럭시에 .10을 데이터 보존 업데이트했다. 실기기 `bubble-gestures`는 실제 overlay 좌표와 주입 터치로 간격·64dp 영역·즉시 이동·편집기 갱신 후 유지·취소 복원·왼쪽 메뉴·터치 녹음·키보드 숨김을 검증했다.
- 기존 18개 기기 시나리오도 통과했다. `recovery-states`는 프로덕션 복구 View/모델을 QA 앱에서 실행해 전문 표시·오래된 복사 거부·삭제·빈 상태를 확인하며 사용자 클립보드는 덮어쓰지 않는다. 서버 실패부터 복구 화면까지의 실제 발화 전체 경로를 모의 데이터 UI 검사로 대체했다고 주장하지 않는다.
- 검사는 대화를 보내거나 음성을 서버에 업로드하지 않는다. 자동 검사가 새 실발화 전사·문장 삽입 검증을 대신하지 않는다.
- 새 APK는 로컬 산출물이며 GitHub push·새 릴리스·기존 릴리스 자산 교체는 이번 작업에서 하지 않는다.

### 최종 설치 확인

녹음 전환·task 분리 수정본 `.10`(해시 `CA3F7874…`)에서 **21개 기기 시나리오 전부 통과**, 실제 **Grok 3/3·ChatGPT 3/3**의 녹음 시작·키보드 숨김·창 유지·Home 취소가 통과했다. 설정 방문 후 녹음 경로를 포함한다. 실제 ChatGPT 화면에서 입력칸 상단과 버튼 하단의 간격은 108px(기기 density 2.25에서 48dp)이었다. 그 화면에는 개인 사이드바가 있어 Git에 첨부하지 않았다.

그 뒤 수동 위치에도 입력칸 위 안전 범위를 적용하는 계산만 추가하고 Java 114개·전체 APK/QA 빌드·Lint·서명을 재검증했다. 사용자가 휴대폰에서 다른 앱을 사용 중이어서 화면 조작을 중단했고, 활성 녹음창이 없음을 확인한 뒤 최종 APK만 데이터 보존 업데이트했다. 이 마지막 좌표 제한의 별도 실기 제스처 재검증은 하지 않았다. 임시 QA 앱·기기 임시 캡처는 제거했다.

**남은 사용자 설정 정리:** 마지막 읽기 확인에서 모드는 QA가 선택한 `깔끔하게`, 수동 좌표는 x=1.0/y=0.43487507이다. 사용자 조작과 겹치지 않도록 위치 초기화·선호한 최소 모드 복원을 멈추고 잠시 조작 중단 가능 여부를 물었다. 답변 전에는 임의로 화면을 전환하거나 추가 터치하지 않았다. 앱의 `마이크 위치 초기화`와 모드 선택으로 바꿀 수 있다. 최종 좌표 제한은 이 저장된 위치도 현재 입력칸 위로 제한한다.

설치된 `base.apk`와 로컬 APK의 SHA256이 일치한다.

```text
C3FAE5107378B2E1EED69B5AE63E73C9D5668B3A3ED3BC480935A5AB31A31EAE
```

산출물: `output/android/Ultra-STT-1.1.62-android.10-debug.apk`. 기존 서명 키·앱 데이터·서버 인증을 유지했다. 기본 키보드는 Samsung HoneyBoard이며 키보드 정책은 원래 값 0으로 돌아갔다. 실제 사용자 발화의 서버 왕복·문장 삽입은 자동 검사와 별도의 수동 확인 항목이다.
