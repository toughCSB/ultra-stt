# 긴 녹음·입력 복구·자동 실행 점검 — 2026-10-11

> **후속 적용 완료:** 이 문서는 원인 조사 당시의 이력이다. 이후 사용자 승인으로 SB·Home·Mac에 수정 1.1.64를 설치했다. Windows 대화형 세션의 전체 검사도 통과했다. 최신 설치·검증 범위는 [데스크톱 업데이트 기록](2026-10-11-desktop-update.md)을 따른다.

## 실제 확인한 기록

설치본을 종료하거나 교체하지 않고 설정과 SQLite 기록을 읽기 전용으로 조회했다. 원격 인증 값과 전사 전문은 이 문서에 넣지 않았다.

- **Home:** `ultra-remote`, 녹음 상한 600초, 자동 실행 활성, `start_minimized=false`.
- Home DB의 `2026-10-11T14:46:12` 기록: `duration_ms=289450`, 결과 1,073자, `clipboard_fallback`. 사유는 `The target app changed before output; the full text was copied instead.`였다. 이 기록은 **전사 유실이 아니라 자동 입력 차단**이며 기존 기록에서 다시 복사할 수 있다. 시간은 DB에 저장된 문자열 그대로다.
- Home의 `2026-10-11T14:50:03` 기록: 결과 958자, `inserted`, 원문/정리 결과 양쪽에 `불명확` 문자열이 있다.
- 다만 기존 원격 클라이언트는 서버의 `raw`를 버리고 `text`를 원문에도 저장했다. 따라서 이 기록만으로 `[불명확: 음성 인식 불가]`를 Whisper가 만들었는지 AI 다듬기가 만들었는지 단정할 수 없다.
- SB 설정의 상한은 300초다. Home 설정 600초와 다르며 임의로 변경하지 않았다.
- 과거 9분 실패 당시 원본 음성과 오류 로그는 이번 조회에서 확보하지 못했다. 현재 SB 실행은 표준 출력으로 로깅하며, 발견한 과거 파일 로그는 최근 실패와 시점이 달랐다. 원본을 복구했다고 주장하지 않는다.

## 확인한 코드 결함과 수정

### 녹음 상한과 처리 제한 불일치

기존 로컬/Whisper 요청은 60초, 원격 처리와 파이프라인 대기는 120초였다. 녹음 상한을 600초로 설정해도 처리 제한은 늘지 않았다. 외부 요청이 진행 중인데 파이프라인 대기만 끝나 빈 전사로 판단할 수도 있었다.

`stt/processing_budget.rs`에서 음성 길이에 따라 처리 예산을 계산하고 **인식 < 원격 AI 포함 처리 < 업로드 요청 < 최종 대기** 순서를 유지하도록 했다. HTTP 재시도도 하나의 전체 요청 예산을 공유한다. 이미 전체 시간을 소진한 timeout에 긴 음성을 다시 제출하지 않는다. 최종 대기 timeout은 인식 불가가 아닌 시간 초과로 보고하고 남은 작업을 취소한다. 녹음 상한 자체나 모델은 변경하지 않았다.

이 변경은 불필요한 조기 중단을 줄이는 것으로, 네트워크·서버 고장까지 없애거나 모든 10분 녹음의 성공을 보장하지는 않는다.

### 전사 성공 후 AI 오류로 원문까지 소실

원격 서버의 AI 다듬기 호출에 `?`가 있어, 전사 원문이 있어도 다듬기 오류 시 전체 요청을 오류로 끝냈다. 이제 AI 실패·빈 결과는 전사 원문으로 반환한다. 클라이언트도 기존 응답의 `raw`를 별도로 보존해 기록의 원문/정리 결과를 구분한다. 응답 형식·인증·모델·AI Fast 정책은 변경하지 않았다.

### AI가 음성을 듣지 않았는데 불명확 표기를 만드는 경우

다듬기 프롬프트에 텍스트만 받은 작업이라는 제약을 추가했다. Codex의 일반 받아쓰기 결과에 원문에 없던 불명확 음성 표기나 빈 결과가 나오면 원문을 보존한다. 원문 자체에 이미 있는 표기는 임의로 삭제하거나 추측해 채우지 않는다. 선택 문장 편집·번역·질문을 일반 받아쓰기로 바꾸지 않았다.

이는 재발 방어이며, 위 실제 기록의 표기 발생 단계를 입증한 것은 아니다.

### 재부팅 후 메인 창이 열림

기존 시작 등록에는 실행 파일만 있었고 `start_minimized=false`이면 창을 열었다. 이제 시작 등록에 `--autostart`를 붙여 메인 창을 보여 주지 않는다. 이미 실행 중인 앱에 자동 실행 요청이 다시 와도 창을 열지 않는다. 사용자가 일반 실행·트레이로 창을 여는 동작은 유지한다. 실행 중인 설치본·시작 레지스트리는 아직 수정하지 않았다.

## 녹색 실행창에 결과가 남는 이유

현재 소스의 `CapsuleRecovery`는 입력 실패 결과를 보여 주고 복사 버튼을 제공한다. Home 기록에서 확인한 안전장치는 **녹음 시작 때의 입력 대상과 완료 때의 대상이 같다고 확인되지 않으면** 자동 붙여넣기를 막고 클립보드/입력 복구로 남기는 것이다.

현재 기록만으로 실제 대상 이동과 일시적 조회 실패를 구분할 수는 없다. 다만 코드상 오탐 경로를 보완했다. Windows 기본 Edit/RichEdit는 UIA 응답 여부에 따라 식별 방식이 바뀌지 않도록 처음부터 같은 HWND 식별자를 사용한다. 웹 입력란은 기존 UIA 요소 식별을 그대로 요구한다. 녹음창 자체에 포커스가 있을 때만 원래 창을 복원하고, 이후 원래 입력란과 다시 비교한다. 다른 외부 앱으로 이동했을 때 강제로 되돌리거나 검증 없이 입력하지 않는다.

## 원본 음성 복구

사용자의 후속 지시 “보완하라고”에 따라 질문을 대기 조건으로 두지 않고 구현했다. 추가 의존성·인증 변경은 없다.

- 앱 데이터 폴더의 `recording-recovery`에 16 kHz mono PCM WAV를 녹음 처리 중 누적한다. 네트워크로 보내기 전에 기록하고 1초 분량마다 파일 헤더와 데이터를 동기화한다. 갑작스러운 시스템 장애에서 마지막 동기화 이후의 데이터까지 보장한다는 뜻은 아니다.
- 전사 원문을 AI 처리 전 별도 TXT로 보관한다. 성공적으로 입력/의도적 복사가 끝난 경우와 사용자가 명시 취소한 경우에만 해당 음성·원문을 정리한다. STT·AI·입력 실패 시에는 보존한다.
- 파일명은 앱이 발급한 UUID로 제한한다. 녹음·재전사 중 삭제/중복 재전사를 차단한다. Unix 폴더/파일은 700/600 권한이며 Windows는 기존 앱 데이터 폴더 권한을 상속한다. 음성은 암호화되지 않은 로컬 WAV이므로 같은 사용자 계정으로 접근할 수 있다.
- 최대 20개 / 512 MiB이며 다음 녹음의 최대 용량을 예약할 여유가 없으면 시작을 막는다. 실패 음성을 오래됐다는 이유로 자동 삭제하지 않는다.
- **입력 복구 → 원본 음성 복구**에서 원문 다시 전사·복사·폴더 열기·2단계 삭제 확인을 제공한다. 다시 전사는 현재 Local / Custom Whisper 설정과 기존 자격 증명을 사용한다. 원격 연결도 AI 다듬기를 끈 원문 전사 요청이며 자동 붙여넣지 않는다. 다른 STT 공급자에는 WAV 폴더를 제공하고 재전사 미지원 오류를 명시한다.
- 적용 범위는 일반 데스크톱 받아쓰기/해당 파이프라인 번역이다. 별도의 Ask 녹음 경로와 Android 저장 정책은 이번 변경 대상이 아니다. 과거 저장하지 않은 원본이 새로 복구되지는 않는다.

## 1차 검증 이력

- 자동 실행 명령 테스트를 먼저 실행해 `--autostart`가 없어서 실패함을 확인했고 수정 후 통과했다.
- 합성 PCM 10분 분량(19,200,000 bytes)을 실제 Whisper-compatible HTTP 요청으로 전달하는 검사에서 모든 PCM bytes 보존을 확인했다. 사람의 10분 발화 정확도 검증은 아니다.
- 가상 시간을 사용하는 검사에서 10분 음성의 처리 결과가 이전 120초 제한 이후에도 정상 완료된다.
- AI 실패/빈 응답 시 긴 원문 보존, 원문에 없는 불명확 표기 거부, 원격 raw/text 분리 검사가 통과했다.
- 최종 관련 Rust 검사 199 통과, 기존 opt-in 3 ignored 유지. STT 117 / remote 7 / Codex 10 / autostart 4 / pipeline 52 / 통합 9.
- `cargo fmt --check`, `cargo clippy --locked ... -- -D warnings`, 프런트엔드 production build 통과.
- 전체 Rust 실행에서는 당시 664 통과, 1 실패, 기존 3 ignored였다. 실패는 수정하지 않은 `capsule_window.rs`의 `restores_native_z_order_without_activating_or_reopening_hidden_windows`에서 `is_above(capsule, covering)` assertion이다. 독립 실행에서도 재현됐다. 이 검사를 제외하거나 전체 통과로 표시하지 않았다. 이후 raw/text 보존 수정은 위 최종 관련 검사로 검증했다.
- 설치된 앱으로 사람의 실제 녹음·자동 입력·재부팅 후 트레이 동작을 검증하지 않았다. 설치/재시작·푸시/릴리스도 하지 않았다.

로컬 로그: 저장소 밖 `qa/startup-red-20261011.log`, `qa/long-recording-native-20261011.log`, `qa/long-recording-focused-20261011.log`, `qa/long-recording-clippy-20261011.log`.

## 보완 후 검증과 남은 경계

- 프런트엔드 전체 443개와 검증 실행기 7개, 서식·타입·린트 통과. 원본 재전사/실패 보존/명시 삭제/활성 녹음 차단 UI 회귀 검사를 포함한다. 10개 언어 메시지 키 일치도 통과했다.
- Rust 전체 674 통과 / 기존 최상단 창 검사 1 실패 / 기존 opt-in 3 ignored. 별도 통합 검사 9 통과. 10분 WAV의 전 바이트 및 재시작 후 원문 보존, 실패 재전사 후 보존과 재시도 성공, 꽉 찬 저장소에서 기존 자료 비삭제, 쓰다 끊긴 마지막 PCM sample을 제외한 정상 sample 복원을 검증했다.
- 최상단 검사를 조사하니 현재 명령 실행은 Windows **SessionId=0**, 실제 Explorer/앱은 **SessionId=1**이었다. 검사 창은 표시 요청 후에도 `IsWindowVisible=0`, foreground는 null이다. 기존 검사를 끄거나 통과로 바꾸지 않았고, 임시 진단 변경은 모두 되돌렸다. 대화형 사용자 세션의 재검증이 남는다. [Win32 표시 동작 문서](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindow)도 확인했으나 첫 ShowWindow 인자 문제만으로 해결되지는 않았다.
- Chromium에서 실제 복구 컴포넌트의 표시·재전사 결과 갱신을 확인했다. 데이터와 IPC는 전용 예시이므로 실제 마이크/서버 검증과 다르다. 미리보기는 저장소 밖 `qa/recovery-preview-20261011.mjs`이며 개인 음성은 사용하지 않았다.
- npm 보안 검사 취약점 0. 설치된 앱·설정·자동 실행 레지스트리는 아직 변경하지 않았다. SB/Home/Mac 실사용 음성·입력·재부팅 검증과 macOS 빌드는 남아 있다. GitHub 반영도 하지 않았다.

서식·타입·린트·Clippy(`-D warnings`)와 프런트엔드 production build는 통과했다. Windows release 빌드는 별도 후보이며 설치본과 구분한다. 원격 경로의 효과를 적용하려면 SB의 서버 기능과 Home 클라이언트를 모두 갱신해야 한다. 현재 설치 앱에서는 새 원본 음성 복구 화면을 사용할 수 없다.

최종 Windows release 빌드와 해당 실행 파일의 UIA helper 통합 검사 3개가 통과했다. 파일은 `src-tauri/target/release/ultra_stt.exe`, SHA256 `C5B0D965092A3DE9E7659870EFBDDDDE9C7E79EA5ECB87AB4D643F806A14772B`다. 사용자 설치 폴더가 아닌 빌드 산출물이다. 버전은 기존 미배포 소스 1.1.64를 유지했으며 새 NSIS 패키지나 릴리스 태그는 만들지 않았다. 링크 시 라이브러리 생성 안내가 warning으로 표시됐으나 빌드는 exit 0이었다. 실제 마이크 전사·입력 성공의 증거로 해석하지 않는다.

최종 로컬 검사 로그는 저장소 밖 `qa/long-recording-{frontend,native,integration,clippy,release}-final-20261011.log`에 있다. 단일 `npm run verify`는 최상단 검사 1건으로 실패했으며 이를 전체 통과로 보고하지 않는다.

이전 CI 수정, 기존 미추적 조사 문서 3개 및 사용자 앱/인증/기록/설정은 보존했다. 작업 중 만든 읽기 전용 SSH 클라이언트가 출력을 반환한 뒤 종료되지 않아 해당 프로세스만 정리했으며 기존 사용자 SSH 연결은 유지했다.

## 후속 설치·화면 장애 정정

위 검증 경계는 구현 직후의 기록이다. 이후 대화형 Windows Session 1에서 최상단 창 검사를 포함한 전체 검증이 통과했으며 SB/Home/Mac 설치를 진행했다. 다만 초기 Windows 설치는 production feature 없는 release 빌드 탓에 `localhost` 화면 로딩 장애가 발생했다. Home 사용자 신고로 확인해 이전 앱을 복원한 뒤 SB/Home을 정상 Tauri production 빌드로 교체했다. 기존 실패 음성을 삭제하지 않았고 설정·기록과 함께 체크섬으로 보존을 확인했다. 최신 해시와 실제 검증 범위는 [설치 보고의 정정](2026-10-11-desktop-update.md#windows-화면-로딩-장애-정정--2019)을 따른다. 초기 후보의 빌드 성공이나 helper 검사만을 GUI/음성 성공으로 해석하지 않는다.
